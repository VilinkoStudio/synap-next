# 003 产品形态

这里只谈打开之后的界面。存储分层见 [002 架构](002-architecture.md)。

## 不要做成微信小程序

小程序的路径是：

> 安装插件 → 出现一个插件首页 → 用户进入插件做事。

每多一个插件，就多一个入口、一套导航、一套红点。人要记住「这件事去哪个小程序里做」。内容被插件边界切开，首页展示的是功能，不是正在看的东西。这是我们明确不要的。

对象管理器也不要当首页。Entity、Type、Relation 可以存在，作为全部数据或插件卸掉之后的只读退路，不作为每天打开的第一眼。

## 借鉴 VS Code 的机制，不照搬它的外观

要的是 Contribution Model：宿主先有一套稳定的工作台和扩展点，插件往扩展点里贡献能力。

```text
用户正在看某份内容
        ↓
宿主知道当前对象和上下文
        ↓
插件贡献的动作、视图、面板出现在这里
```

不是「多一个插件就多一块 UI」。宿主拥有流程，插件拥有能力。界面是两者按当前上下文拼出来的。

VS Code 的 Activity Bar 不要学。给每个插件一个左侧图标，装多了还是超级 App。槽位主要不是「左边第几个、底部多一个 Tab」，而是语义槽位：

| 扩展点 | 插件在什么时候进来 |
| --- | --- |
| Capture | 用户正在记录或导入 |
| Reader | 用户打开一个对象，插件决定怎么呈现、怎么编辑 |
| Actions | 用户选中对象，插件提供能做的动作 |
| Context | 来源、关系、版本、分析等补充，贴在当前对象旁边 |
| Workspace | 用户保存的一组看法和工作状态，不是新数据库 |
| Background | 没有界面的后台工作 |

插件声明「在这种上下文里我能提供什么」。宿主决定它最后是按钮、菜单、命令、侧栏还是暂时占满工作区。同一插件不能自己造通知中心，也不能要求把内容复制进自己的存储。卸掉之后，对象回到通用可读视图，不留下一个坏掉的入口。

## 工作台长什么样

始终只有一个主工作区，里面是当前内容。人要随时能回答三件事：我在哪、正在处理什么、下一步能做什么。

插件变多时，主工作区不分裂成一排应用图标。Todo 加强的是「处理当前这件事」，Wiki 加强的是「把当前材料组织起来」，知识库分析加强的是「在旁边给出一种看法」。它们从上面的槽位进来。用户主动要一种完整看法时，某个投影可以暂时占满中间，甚至全屏；退出后回到同一份内容，而不是回到某个插件首页。

零额外插件时，工作台已经能用：记下、打开最近的东西、搜索、对未知类型做只读、导入导出。第一方能力也走同一套扩展点，不走一条特权界面。

## 和各端界面的关系

工作台的结构各端相同：一个当前内容，加上按上下文出现的动作和补充。手机可以收成单栏和底部动作，桌面可以放侧栏。插件不规定像素和控件，只提供语义。

Flutter 负责把这些槽位画出来。具体控件库还没定，见架构篇。不管最后怎么画，不能为了「像系统」给每个插件各做一个小程序页面。
