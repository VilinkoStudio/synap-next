# 003 产品形态

这里只谈软件打开之后是什么感觉、界面与插件之间怎么划边界。存和算见 [002 架构](002-architecture.md)。

一句话：**插件负责"结构感"，宿主负责"池子感"。** 底层互通只是必要条件；如果用户感受不到互通，体验上它仍然是一堆小程序。

## 一、一切 UI 皆投影：给独立页面，但不造孤岛

过去曾想过把所有功能都塞进一个“主工作区 + 侧边栏槽位”里，避免做成一堆小应用。但真实使用中，刷一套题、排一个看板、浏览双链图谱、管理待办清单，天生就需要完整的独立页面和专属交互空间，硬塞进侧边栏只会处处掣肘。

所以我们**明确允许视图拥有完整的独立页面**。它之所以不会退化成“微信小程序”，区别不在有没有独立页面，而在三处：

* **小程序共享平台，不共享数据和类型：** 每个小程序各自建库，装十个就是十个互相隔绝的盒子。这里每个页面只是同一池子数据的不同切面（投影）。
* **视图只认能力，不认类型：** 视图声明的是 Trait bound（如 `Checkable + HasText`），而不是"我服务于待办插件"。任何满足 bound 的实体——不管是待办、笔记里挂了勾选的一页、还是复盘里的一条行动项——都能出现在同一张清单里。
* **用户从不"进入一个应用"：** 用户打开的是**对象**或**视图实例**，不是插件。

一个检验标准：**A 插件创建的对象，能否在 B 插件的页面里出现、被引用、被操作，而 A 和 B 彼此完全不知道对方存在？** 能，才不是小程序。

由此带来三条核心交互原则：

1. **导航栏钉住的是视图实例，不是应用图标：** 视图实例 = 视图 + 投影 + 参数，例如“收件箱”、“本周未完成的工作待办”、“读书笔记”。它是用户自己的数据，本身是一个实体，**跨设备同步**——换一台设备，导航栏还是那几项，只是渲染器按端形态不同。
2. **实体可以跨视图自由穿行（Lens）：** 同一个 Entity 可以同时出现在多个投影里。点开它时，宿主默认用最匹配的视图呈现；“切换视角”入口列出所有 bound 被它当前能力满足的视图，随时无损切换。比如同一棵 `Tree + HasText` 的树，可以在大纲和思维导图之间来回切。
3. **任何对象可以嵌进任何对象：** 正文里的引用（`ref`）由宿主按被引用实体能满足的**卡片形态**视图就地渲染——日记里嵌一笔账、会议记录里嵌一条可直接勾选的待办。宿主不需要知道被嵌的是什么，嵌账和嵌待办走同一条路。

## 二、宿主的全局层：池子感从这里来

下列能力不属于任何单个插件，全部建立在标准 Trait、`ref` 与公共投影之上：

* **统一捕获（Quick Capture）：** 先记下来，以后再说它是什么。随手一记默认落进收件箱，之后可以挂组件、被引用、被嵌入。
* **全局搜索：** 基于 `HasText` / `Titled` 的常驻索引，跨所有类型。
* **反向链接面板：** 打开任何对象，都能看到谁引用了它，无论对方是什么类型（内核常驻投影 `sys/backlinks`）。
* **按时间聚合：** “今天”视图把今天的笔记、账目、完成的待办放在一起——一个只认 `Temporal` 的投影，任何单一 App 都做不到。
* **冲突中心：** 订阅所有 `Conflict`。冲突精确到字段（“这条待办的备注两边都改了”），而不是“整个对象冲突”。
* **历史时间轴：** CoW 天然保留全部版本，任意对象都可查看历史、回到某个版本。

## 三、不做类型转换：保留原样，查询与组合

一条记录是什么类型，从创建那一刻起就定了，**系统不提供“把笔记转成待办”这类类型转换**。用户想要的效果，用更轻的方式达成：

| 用户想要 | 怎么做 |
| --- | --- |
| 这条笔记也要能勾选 | 给它“标记为待办”：挂上笔记 Schema 声明过的可选勾选组件。还是那条笔记，同时出现在所有待办清单里 |
| 笔记里有一条待办 | 在正文里嵌一个独立的待办对象 |
| 把这段内容整理成一张知识卡片 | “基于此新建”：用原内容预填新卡片，新卡片引用原笔记，原笔记不动 |
| 看所有带截止时间的东西 | 一个 `Temporal` 视图，不管它们是什么类型 |

挂哪些组件、能被当成什么用，都是插件作者用代码声明的；用户只是在声明过的形态之间选择，不需要理解 Trait。

## 四、数据与视图解耦带来的两种常态

* **有数据，不展示（幕后数据）：** 并不是所有存进数据库的东西都要做界面。比如遗忘曲线参数、知识点掌握度、外部同步进来的原始元数据，它们作为数据插件静默躺在底层，参与响应式计算、影响投影排序即可，完全不污染前台界面。
* **同源多视图（一数多景）：** 同一批底层数据，可以同时挂接多个完全不同的视图。比如同一份错题集，平时复习时用“卡片刷题页”，考前复盘时切到“错因统计页”，互不干扰且状态实时联动。

---

## 五、端侧解耦：放弃单视图跨端，用通用视图兜底

要求一个视图同时把桌面横屏和手机竖屏都排得顺手，开发成本极高，结果往往是两边都别扭。因此：

* **单视图只专注一个端形态：** 每个视图明确声明面向横屏（桌面）还是竖屏（手机）。高频场景（如待办）两端都要重度使用时，就分别配一个极简的竖屏视图和一个丰富的横屏视图，它们满足同一组 bound、订阅同一条投影，数据天然同步。
* **缺视图时的优雅降级：** 在电脑上用某个横屏视图写了数据，手机上却没有对应的竖屏视图时，数据不会“打不开”。宿主内置的**通用 Trait 视图**就是 bound 最宽松的那个视图，按实体当前具备的能力（`Titled`、`HasText`、`Checkable`、`Temporal`、`Tagged` 等）自动拼出干净的阅读与基础编辑界面——这些能力的写方法本身是标准的，所以基础编辑在任何设备上都可用。

---

## 六、美学与自由的边界：布局自由，零件受控

既要给视图足够大的表现空间，又要防止装了五六个插件后整个软件风格割裂，边界划在“布局归视图，零件归宿主”：

* **视图拥有画布和排版权：** 决定这一页是两栏、三栏、瀑布流、卡片堆叠还是答题流，自己组织页面内的交互流转。
* **宿主锁死设计系统：** 字体排版、配色体系、暗黑模式、圆角间距以及基础交互组件（列表、卡片、输入框、按钮、弹窗、Markdown 渲染块、标签等）全部由宿主统一提供。视图只用宿主给的零件搭页面，不自己调像素。

---

## 七、宿主保持克制：不内置 AI，做好底座

本项目**不把大模型对话框做成主页，也不在客户端里内置 AI 聊天或重型 Agent Harness**。大模型与 Agent 工具迭代极快，写死在客户端里只会让软件迅速臃肿过时。

* **外部 AI 负责生产与编排：** Trait 的写方法与读取形状天然就是一份类型化的工具表与上下文。外部 AI 可以读懂整个池子（“214 个可完成事项，37 个未完成，12 个被这篇周报引用”），写回结构化数据，甚至按用户需求编写新的数据插件或视图。
* **宿主只负责稳健呈现：** 把投影渲染流畅、把组件库打磨顺手，支持顺滑地加载与切换视图。

对人而言，“一池数据”的感觉取决于本篇的宿主与视图设计；对 AI 而言，它由类型系统直接保证。

---

## 八、零插件也能用，卸插件不留坑

即使一个额外插件都不装，官方宿主本身依然是一个完整可用的个人数据工作台：

* 内置标准组件库与基础 Schema（随手记），通用 Trait 视图，以及第二节的全部全局能力，加上本地文件导入导出。
* 第一方内置视图与第三方视图走完全相同的投影与 Trait 接口，不搞特权通道。
* 任何视图插件卸载后，底层数据毫发无损，对应实体自动回退到通用 Trait 视图，钉住的视图实例显示为“缺少视图”而不是死链；任何数据插件归档禁用后，历史数据依然永远可读。
