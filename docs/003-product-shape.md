# 003 产品形态

这里只谈软件打开之后是什么感觉、界面与插件之间怎么划边界。存和算见 [002 架构](002-architecture.md)。

## 一、先想清楚：用户为什么要用它

市面上有两类东西可以参照：

* **专门工具**（待办、记账、日记各一个 App）：单点体验精致，但数据各自封闭。
* **元数据库笔记**（Notion、Tana、Anytype）：数据在一处，但结构要用户自己搭——建库、配关系、写查询。少数人很喜欢，多数人建了三个库就放弃了。

我们要承认两件事。第一，**单点体验上我们正面打不过专门工具**；如果用户眼里这是“一个还行的待办 + 一个还行的记账”，他们一定会离开。第二，**“跨领域互通”本身对用户几乎没有价值**——没人需要在待办列表里看到上个月的账单。为了展示架构而做的聚合界面，是为架构服务的伪需求。

真正的空间在于人使用记录的方式：

> **按类型生产，按情景消费。**

记的时候，人是按类型记的：这是一笔账、一条待办、一篇日记，此时需要专注的工具。用的时候，人是按情景用的：这次旅行、这个项目、这学期，此时需要把不同类型的东西放回同一个情景。专门 App 只能做前一半；元数据库笔记能做后一半，但要用户手动关联、自己写汇总。这个架构可以两半都做好，而且不让用户搭任何东西。

所以产品由三部分组成：**专注的工具**、**宿主共享的接缝**、**按情景的聚合**。下面三节分别展开。

---

## 二、工具：允许专注，允许像一个独立 App

刷一套题、排一个看板、记一笔账，天生需要完整的独立页面和专属交互空间。所以**视图可以拥有完整的独立页面**，第一方工具应当做得像精致的独立 App。

它不会退化成小程序，原因在底层而不在界面：

* **小程序共享平台，不共享数据和类型。** 这里每个页面只是同一池数据的一个切面（投影）。
* **视图只认能力，不认类型。** 视图声明的是 Trait bound（如 `Checkable + HasText`），而不是“我服务于待办插件”。一个检验标准：A 插件创建的对象，能否在 B 插件的页面里出现、被引用、被操作，而 A 和 B 彼此完全不知道对方存在？能，才不是小程序。

由此带来几种自然的工作形态：

* **一数多景：** 同一份错题集，平时用“卡片刷题页”，考前切到“错因统计页”，状态实时联动。点开任何实体，“切换视角（Lens）”列出所有 bound 被它满足的视图；同一棵 `Tree + HasText` 的树可以在大纲与思维导图之间来回切。
* **有数据，不展示：** 遗忘曲线参数、掌握度、外部同步进来的原始元数据，只作为数据静默躺在底层参与计算，不污染前台。
* **单视图只专注一个端形态：** 每个视图声明自己面向横屏（桌面）还是竖屏（手机），不强求自动跨端。高频场景两端各配一个视图，读同一条投影，数据天然同步。缺视图时，宿主的**通用 Trait 视图**按实体当前具备的能力拼出干净的阅读与基础编辑界面，任何设备上数据永远打得开。

### 工具之间不转换类型

一条记录是什么类型，从它被创建的那一刻就定了，**系统不提供“把笔记转成待办”这类类型转换**。想要的效果用更轻的方式达成：

| 用户想要 | 怎么做 |
| --- | --- |
| 这条笔记也要能勾选 | “标记为待办”：挂上笔记 Schema 声明过的可选勾选组件。还是那条笔记，同时出现在所有待办清单里 |
| 笔记里有一条待办 | 在正文里嵌一个独立的待办对象 |
| 把这段内容整理成一张卡片 | “基于此新建”：用原内容预填新卡片，新卡片引用原笔记，原笔记不动 |

能挂哪些组件、能被当成什么用，都是插件作者用代码声明的；用户只是在声明过的形态之间选择，从不需要理解 Trait。

## 三、接缝：宿主共享的几样东西

工具各自专注，**接缝由宿主共享**。筛选接缝只用一个标准：普通用户会不会在某个具体时刻感到“这个只有这里能做到”。

* **统一入口：先记下来，不用先选 App。** 输入“午饭 35，和小王”，记账插件认出这是一笔餐饮支出并引用联系人“小王”，收件箱留一条可撤销的提示。机制是标准 Trait `Capturable`：宿主把一段文本交给所有插件，各自返回“能否解释、置信度、构造参数”。它是确定性的，不依赖 AI；插件装得越多，入口越聪明——专门 App 永远只认得自己领域的话。
* **待处理：所有在等我的东西。** 记账里的“待核实”、学习里的“待复习”、读书里的“待整理”都不是待办，但都需要注意。插件通过标准 Trait `Attention`（`{ reason, since, due? }`）声明，宿主提供一个“待处理”入口。结构由插件声明，用户不用配置任何东西。
* **一个搜索框、一份反向链接、一条历史线。** 一个搜索框搜到所有内容；打开任何对象都能看到谁引用了它；CoW 让任何东西都能回到历史版本。
* **冲突中心。** 冲突精确到字段（“这条待办的备注两边都改了”），而不是“整个对象冲突了”。
* **数据属于你。** 本地、加密、可导出；某个插件不再维护，数据依然可读。

明确**不做**：在 A 工具里混入 B 领域的数据、通用的“全部数据”看板、要求用户自己写查询。

## 四、情景：池子露出来的地方

有些事情天然由多种类型的东西组成：**一次旅行、一个项目、一门课、一个人。** 一次日本旅行有行程笔记、订酒店的待办、一路的花费、每天的日记、回来后的复盘。用专门 App，它们散落在五个地方；在这里，它们属于同一个情景。

### 情景是什么

情景就是一个普通实体：标题、正文、可选的时间范围，以及一个成员列表。**成员关系存在情景一侧**，所以任何插件的任何对象都能加入任何情景，插件不需要任何改动；一个对象可以同时属于多个情景（一笔花费既属于“日本旅行”，也属于“2026 年支出”）。情景之间是图，不是文件夹。

### 东西怎么进入情景

如果每样东西都要手动关联，没人能坚持下去。所以分三档：

| 方式 | 怎么发生 | 落在哪 |
| --- | --- | --- |
| **活跃情景** | “进入”日本旅行后，所有新记录自动加入，像手机的专注模式 | 写入：确认成员 |
| **推断** | 落在时间范围内、提到同一个地点或人、AI 判断相关 | 投影：候选成员，淡色显示，点一下确认 |
| **手动** | 拖进来，或在正文里嵌入 | 写入：确认成员 |

**推断归投影，确认归实体。** 候选成员只是一条可以随时重算的投影，规则改了、AI 换了都不会留下脏数据；只有用户确认过的才写成块。

### 情景页：拼成一份文档，而不是仪表盘

最容易做错的，是把情景页做成“记账卡片 + 待办卡片 + 日记卡片”拼起来的仪表盘——那又成了小程序拼盘。情景页应当是**一份由结构化碎片拼成的、非结构化的文档**：

1. **用户自己写的正文**，可以嵌入任何对象；
2. **自动时间线**，成员按时间排开，读起来像一个故事：`3/1 订机票 ¥3,200 → 3/2 办签证 ✓ → 3/5 日记“浅草的早晨” → …`；
3. **插件贡献的摘要**：记账给出“总计 ¥8,200，按类别”，待办给出“还剩 2 件”。情景页不认识任何插件，装了新插件就自动多一张摘要。

### 情景有生命周期

| 阶段 | 用户在做什么 | 页面重心 |
| --- | --- | --- |
| 筹备 | 订票、列清单 | 待办、计划 |
| 进行中 | 随手记 | 活跃情景、快速记录 |
| 回顾 | 复盘、写游记 | 时间线与摘要 |
| 归档 | 偶尔回看 | 一份可搜索的回忆 |

过去的情景可以成为下一次的起点：“像上次日本旅行那样准备”，就是基于旧情景新建，复用当时的清单。数据库越用越懂你，指的就是这个。

**“今天”“本周”就是以时间范围为边界、成员靠推断得到的隐式情景**，复盘因此天然有了素材。

## 五、组合：一切页面都是视图套视图

情景页里嵌入其他插件的摘要，首页上排着几块磁贴，正文里嵌着一笔账——这些都是同一件事：**视图嵌入视图。**

嵌入只有一条铁律：

> **按契约嵌入，不按名字嵌入。** 视图只能说“这里要显示这类能力的东西、以这种形态”，不能说“这里要用某某插件”。

按名字嵌入，对方没装页面就坏了；按契约嵌入，宿主去找满足条件的视图，找不到就退回通用视图，页面永远不会坏。这是 Trait 的思路在 UI 层的延续。

| 嵌入什么 | 形态 | 例子 |
| --- | --- | --- |
| 一个实体 | `card` | 日记里嵌一笔账 |
| 一组实体 | `summary` | 情景页里的“本次花费 ¥8,200” |
| 一个视图实例 | `tile` | 首页磁贴：“本周待办”、“本月支出” |

视图实例（“哪个视图 + 什么参数”，如“本周未完成的工作待办”）本身是实体、跨端同步，所以**磁贴不是新概念**：首页也只是一个视图，磁贴是它引用的一组视图实例。导航栏钉住的同样是视图实例，不是应用图标。

**布局归视图，零件归宿主。** 视图决定这一页是两栏、瀑布流还是答题流；字体、配色、暗黑模式、圆角间距与基础组件（列表、卡片、输入框、按钮、弹窗、Markdown、标签）全部由宿主统一提供。装多少插件、嵌套多少层，视觉下限都被托住。

## 六、宿主：微内核，精致来自第一方插件

“默认无头、可自举”和“开箱就是精致的 App”并不冲突。宿主只保留那些做成插件就不安全、或会造成循环依赖的东西：

| 留在宿主 | 原因 |
| --- | --- |
| 打开库、解锁密钥 | 插件加载之前就要用 |
| 插件加载与信任管理 | 不能让插件自己决定信任谁 |
| 设计系统与组件库 | “零件归宿主”的前提 |
| 导航框架与视图解析（Lens、嵌入、兜底） | 组合机制本身 |
| 通用 Trait 视图、冲突处理、历史回滚 | 所有插件都坏掉时的安全网 |
| 统一入口的槽位（全局快捷键、手势、系统分享） | 与操作系统对接 |

其余都是**第一方插件，随安装包发行**：随手记、待办、情景、今天、收件箱、搜索界面，乃至入口那个输入框的 UI。第一方与第三方走完全相同的接口，不搞特权通道。

两个测试守住这条边界：

1. **自举测试：** 删掉所有第一方插件，宿主仍能打开库、通过通用视图看到并修改所有数据、处理冲突、安装插件。
2. **吃自己的狗粮：** 第一方插件里没有一行代码用了公开接口以外的能力。情景是最重要的检验——产品最核心的功能都能做成普通插件，插件接口才算够用。

卸载任何视图插件，数据毫发无损，实体回退到通用视图，钉住的视图实例显示为“缺少视图”而不是死链；任何数据插件归档后，历史数据依然永远可读。

## 七、第一次打开：选一套预设

既然导航、首页、磁贴、情景模板都是实体，**一套布局就是一包数据**：

```
预设“学生”
  启用插件：随手记、待办、课程、错题本、情景
  导航：    [今天, 待办, 课程, 情景]
  首页磁贴：[本周待办(中), 待复习(小), 本月支出(小)]
  情景模板：[一门课, 考试周]
```

首次打开时选一个预设（学生 / 职场 / 旅行 / 自定义），实际上只是写入几个实体、启用几个插件。预设是数据不是代码，所以可以分享、导入，也可以让 AI 生成（“我是研究生，帮我配一套”）。普通用户永远只是选预设、偶尔拖动磁贴；编辑嵌套组合属于高级功能。

## 八、AI 的位置

本项目**不把大模型对话框做成主页，也不在客户端里内置聊天或重型 Agent Harness**——它们迭代太快，写死在客户端里只会让软件迅速臃肿过时。但 AI 是核心体验的一部分，而不是外挂：

* **看得懂整个池子：** Trait 的读取形状与写方法天然就是一份类型化的上下文与工具表。AI 看到的不是一堆 Markdown，而是“214 个可完成事项，37 个未完成，12 个被这篇周报引用”。
* **情景就是现成的上下文：** 不必再手动把材料整理进一个对话；“关于日本旅行的一切”已经在那里。情景同时是授权边界——授权 AI 读“日本旅行”，而不是整个库。
* **连接你自己的 AI：** 宿主提供连接入口（API Key 或 MCP），让 AI 参与统一入口的识别、情景的推断、复盘的起草。没有 AI 时，这些功能退回确定性的底子，依然可用。
* **长尾的个人工具：** 专门 App 只覆盖最大众的十种需求。追踪吃药、记健身组数、管收藏的酒、刷某本教材的题，这些小需求从来没有好工具。对 AI 说一句“帮我做一个记录健身的工具”，它写出数据插件与视图；这个小工具一出生就自带同步、加密、历史、搜索、统一入口、待处理与情景。v1 先在桌面经由 MCP 跑通这条闭环，运行时下发视图留给声明式视图描述（见 007）。

对人而言，“一池数据”的感觉来自本篇的工具、接缝与情景；对 AI 而言，它由类型系统直接保证。

## 九、v1 要验证什么

v1 不和专门工具比单点体验，只验证两个赌注：**接缝与情景**让人留下来，**长尾工具**让人进来。

* 第一方工具只做两三个，而且必须精致：随手记、待办，加上记账或读书中的一个。
* 宿主把统一入口、待处理、今天做透；情景支持手动创建与加入、活跃情景、时间线与至少两个插件的摘要。推断成员留到后续版本。
* 跑通一次“说一句话 → 出现一个能用的小工具”。

判断标准只有一个：**用户真的经历过一次情景之后，会不会回头翻那一页，并且觉得用几个专门 App 拼不出来。**
