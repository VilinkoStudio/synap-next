# 001 哲学

## 我们实际遇到的事

一个人会把记录拿去干完全不同的事：随手记下一段话、列一个待办、给 AI 备一份知识库、写一篇复盘。旧 Synap 想用一套结构把它们全装进去：片段、Tag、用“接着说”连成的 DAG。写的时候很干净，用起来开始别扭——待办要假装成一段话的后继，还要配一套复杂的元数据 Tag 管完成状态。

问题不在原语太少，在**组织方式被提前写死了**。一种结构一旦升成唯一的世界模型，就开始规定人该怎么用。

但如果反过来，每种用途各写一个 App、各建一套库，又会掉进另一个坑：版本、加密、同步、缓存失效、前端状态管理，每做一个新应用都要重造一遍轮子；更重要的是，同一个人的材料散在好几个孤岛里，既无法互相转化，外部工具与 AI Agent 也无法完整地理解这个人。

所以要分开两件事：**统一底座，放开用法。**

## 这不是概念拼盘，而是一台咬合的机器

很多系统把存储、同步、查询、缓存做成四个互相打架的模块：改了数据要手动清缓存，加了同步就要给数据库打冲突补丁。

本项目的核心赌注，是把底层压缩到极少的原语，但让它们在机制上**高度耦合、互相成就**。整套设计围绕三个咬合点展开：

### 咬合点一：同步与响应式，是同一枚硬币的两面

底座的物理基石是一个**厚实的 `Block**`——它天生自带 CoW（只增不减，只有 CR 没有 UD）、压缩、加密和 Merkle-DAG 校验链。把这些能力做进最底层的原语，不是为了堆功能，而是因为**不可变块同时解开了同步和响应式两个死结**：

* **对同步来说：** 因为块不可变、没有全局线性日志，多端同步退化成纯粹的**集合并集**，存储层绝对零冲突。
* **对响应式来说：** 传统数据库做实时计算最怕“原地修改导致读到脏数据”。而在 CoW 底层上，任何修改（无论是本机写入，还是远端同步过来的新块）都只是追加新块并推进本机的 `LocalSeq`。
* **两者怎么合作：** `LocalSeq` 把“本机写入”和“多端同步到达”统一成了同一条本地心跳。引擎拿到新旧不可变块，直接算出确定的变更增量（`Delta`：旧值 `-1`，新值 `+1`）推入计算图。**同步进来的数据，天然就会驱动本地所有视图和索引自动刷新，不需要任何胶水代码。**

### 咬合点二：面向能力的持久化组合（Entity + 插件 + Trait）

在物理 `Block` 之上，逻辑世界由 `Entity`（实体）构成。一个 `Entity` 不是传统数据库里死板的一行表记录，而是由一组父子 `Block` 串起来的演化历史（DAG）。

内核本身不理解这些字节是什么意思，解读权完全交给 **Data Plugin**（LuaJIT 沙箱），跨插件的复用则交给 **Trait**：

* **Code as Data：** 数据插件的源码本身也作为 `Block` 入库，随数据一起多端同步。卸载插件只是禁用它的创建权，历史数据永远带着自己的“说明书”，永远可读。
* **Trait 是数据的通用接口：** 类似 Rust 的 Trait 或嵌入式的 `embedded-hal`。Todo、Wiki、个人记录各自维护自己的内部结构，但只要它们都暴露了 `Checkable` 或 `HasText`，上层就能跨应用复用。同一个插件的 v1/v2 版本也能无缝共存，不需要停机迁移。
* **冲突也被吸纳进了同一套机制：** 多端离线修改同一个 `Entity` 会产生多个最新节点（多 Head 分叉）。内核不硬编码合并规则，而是把分叉列表交给插件：能自动收敛的在读时收敛，必须人介入的（如正文冲突、删改冲突、或跨实体的 DAG 成环）统一暴露为 `trait.Conflict`，最终由一次普通的写操作闭合分叉。

### 咬合点三：查询、索引与自动缓存的终极统一（Projection）

在这个数据库里，没有 SQL，也没有单独的“索引”或“视图”概念——它们全被统一成了 **Projection（投影）**。

* **一切皆计算图：** 投影是基于 Trait 搭起来的增量计算图。所有算子都遵循“吃 Delta、吐 Delta”的闭环，因此无论查询规则怎么嵌套组合，天然都是 100% 增量响应式的。反向索引本质上只是一个展开键值的常驻投影。
* **缓存是计算图的自然副产品：** 传统 App 要自己写 ORM、维护缓存失效、管前端状态同步；在这里，数据库内核直接接管了依赖图。正在打开的界面和常驻索引是存活锚点（Roots），锚点可达的节点实时热更新；界面关闭后节点降级休眠，短时间切回只需补算落下的 `LocalSeq` 增量，内存吃紧时自动回收。
* **上层只管画界面：** 当底层把存储、同步、索引和响应式缓存全部消化掉之后，上层的 **UI Plugin** 就变得极轻——它不碰存储，只负责“订阅投影 → 渲染 → 通过 Trait 接口写回”。

## 边界：内核与两类插件的分工

把“存算”和“展示”彻底切开，系统边界非常干净：

* **内核（Rust，无头）：** 只管 `Block` 存储、加解密压缩、无冲突同步、LuaJIT 沙箱调度和响应式计算图。它永远不知道“待办”或“笔记”是什么；如果某个插件离了内核里的业务字段就写不出来，优先怀疑是原语不够，而不是把业务塞进内核。
* **Data Plugin（LuaJIT，进库同步）：** 定义结构、校验写入、提取 Trait、处理分叉。只能归档，不能物理删除。
* **UI Plugin（客户端宿主，纯本地）：** 负责交互与渲染，不进块存储，随时可换、可删，与数据插件彻底解耦。

本项目本身不内置大模型调用。内核从第一天起就提供完整的结构化对外接口与带上下文的插件执行能力，既托起自己的官方客户端，也平等地向外部脚本、工具与 AI Agent 开放。

## 核心术语

这些词在后面文档里反复出现，先一次定死。概念解释以这里为准，Rust 定义归 core，读写语义归 store，计算语义归 runtime。

| 术语 | 定义 |
| --- | --- |
| **Block** | 物理最小单位。不可变，自带压缩、加密与校验链。`BlockHash = Hash(规范化逻辑内容)`，与压缩加密后的物理字节无关。固定头部（信封）+ 裸字节负载。 |
| **Entity** | 逻辑对象（如某条待办）。`EntityId` 标识，生命周期 = 一组父子串起的 Block（DAG）。 |
| **Head** | 某 Entity 无子节点的最新 Block。正常 1 个；多端离线并发时多个（多 Head 分叉）。 |
| **LocalSeq** | 本机自增 `u64`，永不参与同步。每落盘一块（无论本地写入或远端同步）+1，驱动本机响应式引擎。只是到达流水，不是可重放的 Delta 日志。 |
| **Hlc** | 混合逻辑时钟，跨端排序用。 |
| **Blob** | 大二进制内容的独立块。快照里只存其内容哈希，不内嵌字节。 |
| **Data Plugin** | Lua 纯函数模块，本身也作为 Block 入库。负责编解码、创建/变更逻辑、Trait 提取与冲突收敛。 |
| **UI Plugin** | 图形插件，由客户端宿主解析执行，不进块存储。订阅投影渲染，通过标准 Trait 接口写回。 |
| **Trait** | 跨插件能力契约（如 `Create`、`Checkable`、`HasText`、`Conflict`）。上层只认 Trait，不认插件。命名保留 `Trait`，不用 `Struct`；结构侧叫 Schema，实例侧叫 Entity。 |
| **Conflict** | 冲突记录。单实体多 Head 由插件 `resolve` 收敛；跨实体约束破坏是带 `participants` 的独立记录，不挂靠任何单个 Entity。 |
| **Projection** | 统一的查询/索引/视图/缓存：基于 Trait 的响应式计算结果，底层自动增量维护并管理生命周期。身份 = 名字 + 计算定义版本（见 006）。 |
| **Delta** | 计算图中流动的最小单位 `(Key, Value, Weight)`：`+1` 新增，`-1` 撤销。旧值更新 = 先 `(key, old, -1)` 再 `(key, new, +1)`。 |
| **Tombstone** | 逻辑删除块。保证“删除事实”同步全端；删与改谁赢由 `resolve` 决定，Tombstone 本身不赋予删除优先权。 |

## 为什么是这种拆法

| 做法 | 结果 |
| --- | --- |
| 一种笔记结构通吃 | 旧 Synap 已经试过。跨用途时别扭，并开始规定人怎么记 |
| 每种用途一个独立 App、各存各的 | 版本、同步、缓存、迁移各做一遍；材料散在多处，外部工具也无法共用 |
| **厚实底座 + 响应式投影 + 插件组织** | 存储、同步、缓存由底座一次解决；每种用途用自己的结构，靠 Trait 自由互通 |

第三行是本项目要验证的设计，不是已经证明的结论。

原语长什么样、插件边界在哪、内核怎么算，见 [002 架构](002-architecture.md)。
