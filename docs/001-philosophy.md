# 001 哲学

## 我们实际遇到的事

一个人会把记录拿去干完全不同的事：随手记下一段话、列一个待办、给 AI 备一份知识库、写一篇复盘。旧 Synap 想用一套结构把它们全装进去：片段、Tag、用“接着说”连成的 DAG。写的时候很干净，用起来开始别扭——待办要假装成一段话的后继，还要配一套复杂的元数据 Tag 管完成状态。

问题不在原语太少，在**组织方式被提前写死了**。一种结构一旦升成唯一的世界模型，就开始规定人该怎么用。

但如果反过来，每种用途各写一个 App、各建一套库，又会掉进另一个坑：版本、加密、同步、缓存失效、前端状态管理，每做一个新应用都要重造一遍轮子；更重要的是，同一个人的材料散在好几个孤岛里，既无法互相转化，外部工具与 AI Agent 也无法完整地理解这个人。

所以要分开两件事：**统一底座，放开用法。**

## 这不是概念拼盘，而是一台咬合的机器

很多系统把存储、同步、查询、缓存做成四个互相打架的模块：改了数据要手动清缓存，加了同步就要给数据库打冲突补丁。

本项目的核心赌注，是把底层压缩到极少的原语，但让它们在机制上**高度耦合、互相成就**。整套设计围绕三个咬合点展开：

### 咬合点一：同步与响应式，是同一枚硬币的两面

底座的物理基石是一个**厚实的 `Block`**——它天生自带 CoW（只增不减，只有 CR 没有 UD）、压缩、加密和 Merkle-DAG 校验链。把这些能力做进最底层的原语，不是为了堆功能，而是因为**不可变块同时解开了同步和响应式两个死结**：

* **对同步来说：** 因为块不可变、没有全局线性日志，多端同步退化成纯粹的**集合并集**，存储层绝对零冲突。
* **对响应式来说：** 传统数据库做实时计算最怕“原地修改导致读到脏数据”。而在 CoW 底层上，任何修改（无论是本机写入，还是远端同步过来的新块）都只是追加新块并推进本机的 `LocalSeq`。
* **两者怎么合作：** `LocalSeq` 把“本机写入”和“多端同步到达”统一成了同一条本地心跳。引擎拿到新旧不可变块，直接算出确定的变更增量（`Delta`：旧值 `-1`，新值 `+1`）推入计算图。**同步进来的数据，天然就会驱动本地所有视图和索引自动刷新，不需要任何胶水代码。**

### 咬合点二：结构、能力、视图三分，靠组合生长（Schema + Trait + View）

在物理 `Block` 之上，逻辑世界由 `Entity`（实体）构成。一个 `Entity` 不是传统数据库里死板的一行表记录，而是由一组父子 `Block` 串起来的演化历史（DAG）。

内核本身不理解这些字节是什么意思。解读权交给上层，而上层被明确拆成三件互不混淆的事：

* **结构（Schema）：这东西长什么样、怎么改。** 由数据插件定义，私有。一个实体的 Schema 从创世起终身不变——**不做类型转换**，需要"变成别的东西"时，靠查询与组合，或者由用户显式"基于此新建"。
* **能力（Trait）：它能被当成什么用。** 类似 Rust 的 Trait 或嵌入式的 `embedded-hal`。Trait 是一份公开契约（读取形状 + 写入方法），Schema 必须**用代码显式声明**自己实现了哪些 Trait——名义匹配，不做 Go 式的结构猜测，也不由用户手挂。上层只认 Trait，不认 Schema：只要都实现了 `Checkable`，待办、笔记、复盘就能出现在同一张清单里。
* **视图（View）：一组行怎么画。** 视图声明自己需要的 Trait（bound），像带约束的泛型函数，对任何满足约束的实体都能工作。

三者之间靠**组合**生长，而不是继承：

* **组件（Component）是可复用的结构片段**，自带字段、合并策略、Trait 实现与构造函数。领域 Schema 由组件拼成，能力通过委托自动获得——一个待办由"标题 + 勾选 + 时间"组件拼成，一行实现都不写就具备 `Titled`、`Checkable`、`Temporal`。从内核的 Entity 与 Projection 出发，经由标准组件库，逐层长出整个生态，每层都可跳过。
* **引用（`ref`）是内核唯一认识的关系。** 需要独立身份的东西做成独立实体，用引用组合、嵌入、反向链接；不需要的做成组件。
* **Code as Data：** 数据插件的源码本身也作为 `Block` 入库，随数据一起多端同步。卸载插件只是禁用它的创建权，历史数据永远带着自己的"说明书"，永远可读。同一 Schema 的 v1/v2 读时提升、写时落新，不需要停机迁移。
* **冲突也被组合吸纳：** 多端离线修改同一个 `Entity` 会产生多个 Head。合并按组件逐字段委托——标题取最新、标签取并集、正文做三方合并——插件作者选对组件就自动拥有正确的冲突处理；只有真正合并不了的（如同一段正文两边都改了、删改冲突、跨实体成环）才暴露为精确到字段的 `Conflict`，最终由一次普通的写操作闭合分叉。

类型系统的完整规格见 [006 runtime](006-synap-runtime.md)。

### 咬合点三：查询、索引与缓存是同一件事（Projection）

在这个数据库里，没有 SQL，也没有单独的“索引”或“物化视图”概念——它们全被统一成了 **Projection（投影）**。

* **写起来像迭代器链，跑起来是增量的：** 投影是一条以 Trait 为源的算子管道（`from → filter / map → index`），写法和 Rust 的迭代器或 LINQ 一样。但 runtime 不在整个集合上跑它，而是让每个 `Delta` 流过它。唯一的约束是**闭包只看一条记录**——守住这一条，增量就是自动的，作者不需要知道“增量”这个词。
* **结果是有序索引，读取就是 B-Tree 游标：** 管道的终点是一棵按 key 有序的 B-Tree，排序在写入时完成。前台只用三个原语读它——`get` 点查、`range` 从某个 key 顺着走 N 条、`watch` 监听一段区间。滚动列表、展开导图的成本只与屏幕上的数据量有关，与库有多大无关。
* **维护还是只算一次，由 runtime 决定：** 增量是拿常驻状态换更新速度，只对长期打开的视图和常驻索引划算。同一条管道，有人监听时增量维护，只是问一句时算一遍就丢。树和图的递归不进管道，由用户的展开动作按需读取。
* **缓存是这套机制的自然副产品：** 传统 App 要自己写 ORM、维护缓存失效、管前端状态同步；在这里，正在被监听的区间和常驻索引是存活锚点（Roots），其余按 GC 休眠或回收，切回时只补算落下的 `LocalSeq` 增量。
* **公共投影只吃 Trait：** 面向所有人的投影只能以“实现了某 Trait 的实体”为源，看不见具体 Schema，因此天然覆盖未来才出现的新类型。这是整个池子不碎成孤岛的关键纪律。
* **上层只管画界面：** 当底层把存储、同步、索引和响应式缓存全部消化掉之后，**视图**就变得极轻——它不碰存储，只负责“读取投影 → 渲染 → 通过 Trait 接口写回”。

## 边界：内核、数据插件与视图插件

把“存算”和“展示”彻底切开，系统边界非常干净。注意**插件是分发单位，不是概念层**——一个插件包里装的是 Schema、组件、Trait、Impl、投影定义或视图的任意组合：

* **内核（Rust，无头）：** 只管 `Block` 存储、加解密压缩、无冲突同步、组件组合与合并、LuaJIT 沙箱调度和投影管道的增量执行。它永远不知道“待办”或“笔记”是什么，唯一认识的语义是 `ref`。如果某个插件离了内核里的业务字段就写不出来，优先怀疑是原语不够，而不是把业务塞进内核。
* **数据插件（Lua，进库同步）：** 定义 Schema、组件、Trait 与 Impl，以及私有投影。只能归档，不能物理删除。
* **视图插件（Dart，纯本地）：** 提供视图，负责交互与渲染，不进块存储，随时可换、可删，与数据插件彻底解耦。

本项目本身不内置大模型调用。内核从第一天起就提供完整的结构化对外接口与带上下文的插件执行能力，既托起自己的官方客户端，也平等地向外部脚本、工具与 AI Agent 开放。

## 核心术语

这些词在后面文档里反复出现，先一次定死。概念解释以这里为准，Rust 定义归 core，读写语义归 store，计算语义归 runtime。

| 术语 | 定义 |
| --- | --- |
| **Block** | 物理最小单位。不可变，自带压缩、加密与校验链。`BlockHash = Hash(规范化逻辑内容)`，与压缩加密后的物理字节无关。固定头部（信封）+ 裸字节负载。 |
| **Entity** | 逻辑对象（如某条待办）。`EntityId` 标识，生命周期 = 一组父子串起的 Block（DAG）。 |
| **Head** | 某 Entity 无子节点的最新 Block。正常 1 个；多端离线并发时多个（多 Head 分叉）。 |
| **LocalSeq** | 本机自增 `u64`，永不参与同步。每落盘一块（无论本地写入或远端同步）+1，驱动本机响应式引擎。只是到达流水，不是可重放的 Delta 日志。 |
| **Hlc** | 混合逻辑时钟，跨端排序用。 |
| **Blob** | 大二进制内容的独立块。快照里只存其内容哈希，不内嵌字节。 |
| **Schema** | 结构定义：字段、组件组合、私有动作。`SchemaId` 为稳定名义身份（如 `vilinko.todo/item`），`SchemaVersion` 为定义它的插件源码块哈希。一个实体的 `SchemaId` 终身不变。 |
| **Component** | 可复用的结构片段：字段 + 合并策略 + Trait 实现 + 构造 + 升级。只能被组合进 Schema，不能单独成为实体；可声明为可选。 |
| **Trait** | 跨插件能力契约：读取形状 + 写入方法 + 文档，`TraitId@major` 版本化（如 `std/Checkable@1`）。上层只认 Trait，不认 Schema。 |
| **Impl** | `(Trait, Schema)` 的显式实现，名义匹配。遵守孤儿规则：只能写在 Schema 或 Trait 所属的插件里。实例此刻是否具备该能力由 `extract` 返回值决定。 |
| **ref** | 内核唯一认识的语义值类型：指向另一个 `EntityId`。反向链接、嵌入都建立在它之上。 |
| **Conflict** | 冲突记录。单实体分叉按组件合并，合并失败时产生精确到字段路径的记录；跨实体约束破坏是带多个 `participants` 的独立记录。 |
| **Projection** | 统一的查询/索引/缓存：以 Trait 为源、闭包只看一条记录的算子管道，终点是有序 B-Tree 索引，经 `get` / `range` / `watch` 读取。被监听时增量维护并按 GC 管理，否则只算一次。公共投影只吃 Trait，私有投影可吃本插件的 Schema。身份 = 名字 + 计算定义哈希。 |
| **View** | 视图：声明 Trait bound 与形态（整页 / 卡片），对任何满足 bound 的实体都能渲染。代码在 Dart 侧纯本地。 |
| **视图实例** | “哪个视图 + 绑哪个投影 + 什么参数”，如“本周未完成的工作待办”。属于用户数据，本身是一个实体，跨端同步；导航栏钉住的就是它。 |
| **插件** | 分发单位，不是概念层。数据插件（Lua，进库同步）装 Schema/组件/Trait/Impl/投影定义；视图插件（Dart，纯本地）装视图。 |
| **Delta** | 计算图中流动的最小单位 `(Key, Value, Weight)`：`+1` 新增，`-1` 撤销。旧值更新 = 先 `(key, old, -1)` 再 `(key, new, +1)`。 |
| **Tombstone** | 逻辑删除块。保证“删除事实”同步全端；删改并发默认产生冲突，Schema 可声明自动策略，Tombstone 本身不赋予删除优先权。 |

## 为什么是这种拆法

| 做法 | 结果 |
| --- | --- |
| 一种笔记结构通吃 | 旧 Synap 已经试过。跨用途时别扭，并开始规定人怎么记 |
| 每种用途一个独立 App、各存各的 | 版本、同步、缓存、迁移各做一遍；材料散在多处，外部工具也无法共用 |
| 一个底座上装一堆互不相通的小应用 | 省掉了重复建设，但用户看到的仍是孤岛——这就是小程序 |
| **厚实底座 + 结构/能力/视图三分 + 组合** | 存储、同步、缓存由底座一次解决；每种用途用自己的结构，公共投影与视图只认 Trait，实体跨视图自由穿行 |

第三行是本项目要验证的设计，不是已经证明的结论。

原语长什么样、插件边界在哪、内核怎么算，见 [002 架构](002-architecture.md)；类型系统细节见 [006 runtime](006-synap-runtime.md)。
