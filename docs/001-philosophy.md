# 001 哲学

## 我们实际遇到的事

笔记软件很少只被当成「记一条笔记」。同一个人会把它拿去干完全不同的事：随手记下一段话、做一个待办、维护一份给 AI 用的知识库、留下某段时间的成长记录。这些用途都真实，也都值得做。

旧 Synap 想用一套结构把它们装进去：片段、Tag、用「接着说」连成的 DAG。写的时候很干净，用起来开始别扭。待办要假装成一段话的后继；知识库的整理要假装成同一条话语链；不走这条链的人，会被界面暗示自己「还没整理好」。结构一旦升成唯一的世界模型，就开始规定人该怎么用。

把各种模式往同一种通用结构上套，问题不在「原语太少」，而在**组织方式被提前写死了**。DAG 适合「这段话接着那段话读」，不适合「这件事做完了没有」，也不适合「这份材料在某个视角下被解释成了什么」。硬套会丢语义，也会强迫使用。

## 仍然想统一的是什么

一个人的文字和相关材料，仍然可以放在同一个地方管。版本、同步、身份、能不能被别的工具读到，这些如果每种用途各做一套，人要维护的是好几个库，而不是一种生活。

所以要分开两件事：

- **怎么存**：可以统一。同一套存储单元、同一套基本原语、同一套版本和同步。
- **怎么组织**：不能统一成一种图或一种笔记。Todo、知识库、个人记录各自有自己的结构，由使用它们的那一层来定义。

统一的是底座，不是用法。

## 设计

做一个通用的数据存储单元。它提供数据库级别的储存原语，并带上版本和同步。它不知道「待办」「知识库」「接着说」是什么。

上层插件使用这些原语，做出各自的功能。例如：

- Todo list：完成、截止、列表，是插件自己的结构；
- Loam：面向材料的 AI 知识库，分析、视角、派生，是插件自己的结构；
- 若仍要做个人记录，片段和「接着说」也只是其中一个插件的结构，不再是所有数据的骨架。

插件可以有趣、可以专，可以强迫自己的用户走一条清晰的路径。内核不可以。内核多认一种业务结构，就多一次把别人的用法拧进来的机会。

## 为什么是这种拆法

| 做法 | 结果 |
| --- | --- |
| 一种笔记结构通吃 | 旧 Synap 已经试过。跨用途时别扭，并开始规定人怎么记 |
| 每种用途一个独立 App、各存各的 | 版本、同步、迁移各做一遍；同一个人的材料散在多处，Agent 也无法共用 |
| **统一存储原语，组织交给插件** | 材料在一处，可版本、可同步；每种用途用自己的结构，不互相冒充 |

第三行是本项目要验证的设计，不是已经证明的结论。若某个插件离了内核的某种业务字段就写不出来，优先怀疑是原语不够，而不是该把这个字段升进内核。若内核为了「好用」开始内置 Todo 或 DAG 语义，这条设计就失败了。Trait 是 lens，不是结构：跨应用复用的是能力视角，各自的结构仍在插件手里，不违背上一行的拆法。

## 故事要怎么讲给一起做的人

对外不必先讲「笔记的本质」或某次长谈里的自我连续性。那些是动机的来源，不是产品结构。

跟同事对齐时，按这个顺序说：

1. 同一个人会把记录用于完全不同的事，这些事不该共用同一种组织结构。
2. 旧项目用 DAG 去当通用结构，这条路我们不再走。
3. 我们做的是带版本和同步的通用存储单元，加上一组数据库原语。
4. Todo、Loam，以及以后的个人记录，都是插件。它们自己决定结构，内核只保证存得住、对得上、同步得了。

[002 架构](002-architecture.md) 顺着这四句往下写：原语是什么、插件边界在哪、哪些能力属于内核。不要再从「笔记应该如何被重新理解」推架构。
